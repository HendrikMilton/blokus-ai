1. SYSTEM OVERVIEW
================================================================================

This is an AlphaZero-style reinforcement learning system for the board game 
Blokus. The system learns to play through self-play, using Monte Carlo Tree 
Search (MCTS) guided by a neural network to generate training data.

Key characteristics:
- 4-player game (not 2-player like Chess/Go)
- Large action space (~78-200+ legal moves per turn)
- No external training data - learns purely from self-play
- Uses policy + value neural network heads

Technology stack:
- Python 3.13 with PyTorch for neural network
- Rust for MCTS tree operations (~14x faster than Python)
- PostgreSQL for metrics and checkpoint tracking
- FastAPI for training API endpoints

3. KEY COMPONENTS
================================================================================

3.1 TRAINING LOOP (trainer.py)
------------------------------

The AlphaZeroTrainer class orchestrates the full training process:

- Manages network creation, optimization, and checkpointing
- Coordinates the three training phases per generation
- Reports progress to API for frontend display
- Implements cold-start fixes and anti-collapse mechanisms

Key methods:
- train(): Main loop over generations
- _run_self_play(): Generate games using MCTS
- _run_training(): Update network on replay buffer
- _run_evaluation(): Test new network vs best network
- _save_checkpoint(): Save model weights

3.2 SELF-PLAY & MCTS (self_play.py, mcts_rust.py)
-------------------------------------------------

ParallelSelfPlay class generates training data:
- Runs multiple games in parallel for GPU efficiency
- Uses HybridMCTS (Rust tree + Python NN) for move selection
- Collects (state, policy, value) training examples
- Applies temperature to visit counts for exploration

HybridMCTS class performs tree search:
- Selection: UCB1 formula to pick promising nodes
- Expansion: Neural network evaluates leaf positions
- Backpropagation: Update values along path
- Root policy: Blend NN policy with heuristics (cold-start fix)

ReplayBuffer stores training examples:
- Fixed size (1M examples default)
- FIFO eviction when full
- Recent-weighted sampling (anti-collapse fix)

3.3 NEURAL NETWORK (network.py)
-------------------------------

BlokusNet architecture:
- Input: Board state (10 channels x 20x20) + piece availability (84 values)
- Backbone: 15 residual blocks with 256 channels
- Policy head: Outputs logits over legal moves
- Value head: Outputs win probability [-1, 1]

Input encoding (10 channels):
- Channel 0: Current player's pieces
- Channel 1-3: Other players' pieces
- Channel 4: Current player's valid corners
- Channel 5-7: Other players' valid corners
- Channel 8: Turn number (normalized)
- Channel 9: All ones (bias)

3.4 GAME ENGINE (game.py)
-------------------------

BlokusGame implements Blokus rules:
- 20x20 board, 4 players, 21 pieces each
- First move must cover corner
- Subsequent moves must touch own corner diagonally
- Cannot share edges with own pieces
- Numba-accelerated legal move generation (~9x faster)

Key methods:
- get_legal_moves(): All valid placements
- make_move(): Apply move and update state
- get_state_for_neural_net(): Encode for network
- get_scores(): Count placed cells per player

5. TRAINING PHASES
================================================================================

PHASE 0: HEURISTIC PRETRAINING (one-time at start)
--------------------------------------------------
- Generate random game positions
- Compute heuristic policy scores for each position
- Train policy head to predict heuristic moves
- Purpose: Give network non-uniform initial policy

PHASE 1: SELF-PLAY (each generation)
------------------------------------
- Current network plays games against itself
- MCTS selects moves using network for evaluation
- Collect (state, MCTS_policy, game_outcome) tuples
- Add examples to replay buffer

PHASE 2: TRAINING (each generation)
-----------------------------------
- Sample batches from replay buffer
- Forward pass through network
- Compute policy loss (cross-entropy with MCTS policy)
- Compute value loss (MSE with game outcome)
- Compute entropy bonus (anti-collapse)
- Backward pass and gradient update

PHASE 3: EVALUATION (each generation)
-------------------------------------
- Play 100 games: new network vs best network
- Alternate starting player/position
- If win_rate >= threshold: promote new network to best
- Dynamic threshold decreases when stuck

6. COLD START PROBLEM & SOLUTIONS
================================================================================

THE PROBLEM:
When the neural network starts with random weights, it outputs uniform
probability over all legal moves. This causes MCTS to explore uniformly,
generating uniform training targets. Training on uniform targets reinforces
uniform predictions - a "chicken and egg" problem where no learning occurs.

Symptoms observed:
- Policy loss stuck at ~4.35 = log(78) for 36+ generations
- Policy entropy ~4.0 (uniform distribution)
- Top-1 move probability ~0.01 (1/N)
- Win rate stuck at 25% (random among 4 players)

SOLUTION 1: HEURISTIC BOOTSTRAPPING
- Compute handcrafted move scores based on:
  - Piece size (prefer larger pieces early)
  - Center proximity (prefer center positions)
  - Corner creation (prefer moves creating more corners)
  - Edge avoidance (avoid board edges)
- Blend heuristic policy with NN policy at MCTS root
- Gradually decay blend factor over 30 generations

SOLUTION 2: INCREASED MCTS SIMULATIONS
- Start with 1600 simulations (vs 400 base)
- More simulations help MCTS find good moves even with uniform prior
- Decay to base over 20 generations as policy improves

SOLUTION 3: TEMPERATURE-ADJUSTED TARGETS
- Apply temperature 0.5 to MCTS visit counts
- Makes near-uniform distributions more peaked
- Provides stronger learning signal

================================================================================
7. ANTI-COLLAPSE FIXES (NEW)
================================================================================

THE PROBLEM: SELF-DISTILLATION COLLAPSE
After initial learning, the system can get stuck in a loop:
- Model A becomes "best" with win rate 55%
- Model B trains to copy Model A perfectly (92% top-1 accuracy)
- Model B can't beat Model A (they play identically)
- Win rate stays at 40-50%, below promotion threshold
- Entropy collapses: 2.2 → 0.2 (near-deterministic)
- Training stagnates indefinitely

FIX 1: ENTROPY REGULARIZATION
- Add entropy bonus to loss function
- Loss = policy_loss + value_loss - entropy_weight * entropy
- Penalizes overly confident (low entropy) policies
- Adaptive weight increases when entropy too low

FIX 2: DYNAMIC PROMOTION THRESHOLD
- Track generations since last promotion
- After 2 stuck generations, lower threshold by 2%
- 55% → 53% → 51% → ... → 45% minimum
- Allows "good enough" models to become new baseline
- Resets to 55% after promotion

FIX 3: RECENT-WEIGHTED REPLAY SAMPLING
- Instead of uniform sampling from replay buffer
- Weight recent examples ~10x more likely (bias=0.7)
- Exponential weights: exp(0.7 * (position/total - 1) * 3)
- Prevents training on stale data from old model

FIX 4: ADAPTIVE DIRICHLET NOISE
- When entropy < 0.5, increase exploration noise
- Multiply dirichlet_epsilon by entropy_threshold/entropy
- Cap at 2x multiplier (epsilon max 0.5)
- Forces exploration when policy becomes too confident

8. DATA FLOW
================================================================================

Training Example:
┌─────────────────────────────────────────────────────────────────┐
│ TrainingExample                                                  │
├─────────────────────────────────────────────────────────────────┤
│ board_tensor: np.ndarray (10, 20, 20) - encoded board state     │
│ pieces_vector: np.ndarray (84,) - remaining pieces per player   │
│ policy: np.ndarray (N,) - MCTS visit distribution               │
│ legal_moves: List[Move] - legal moves at this position          │
│ value: float - game outcome from this player's perspective      │
└─────────────────────────────────────────────────────────────────┘

Self-Play Flow:
1. Initialize game state
2. While game not over:
   a. Get legal moves
   b. Run MCTS (400-1600 simulations)
   c. Store (state, MCTS_policy, player)
   d. Sample move from policy
   e. Make move
3. Compute game outcome
4. Assign values: +1 winner, -1 losers, 0 ties
5. Add examples to replay buffer

Training Flow:
1. Sample batch from replay buffer (with recent bias)
2. Forward: network(board, pieces) → policy_logits, value
3. Compute policy loss: cross_entropy(policy_logits, MCTS_policy)
4. Compute value loss: MSE(value, game_outcome)
5. Compute entropy: -sum(softmax * log_softmax)
6. Total loss = policy + value - entropy_weight * entropy
7. Backward pass, clip gradients, optimizer step

Key Metrics to Monitor:

1. Policy Entropy (per generation)
   - ~4.0+: Uniform distribution (no learning)
   - ~2.0-3.0: Some focus emerging
   - <2.0: Focused policy (good)
   - <0.5: Possible collapse (bad)

2. Policy Loss
   - ~4.35: log(78), uniform over legal moves
   - <4.0: Better than uniform
   - <3.5: Meaningful learning

3. Top-1 Probability
   - ~0.01: Uniform (1/N)
   - >0.1: Clear preference emerging
   - >0.5: Strong policy (or collapse)

4. Evaluation Win Rate
   - 25%: Random (1/4 players)
   - 35%+: Meaningful improvement
   - 50%: Equal to opponent
   - 55%+: Promotion threshold

5. Value Loss
   - ~1.0: Initial (random predictions)
   - <0.1: Value head learning well

Common Issues:

1. Policy stuck at ~4.35
   - Cold start problem
   - Enable heuristic bootstrapping
   - Increase MCTS simulations

2. Win rate stuck at 40-50%
   - Self-distillation collapse
   - Enable entropy regularization
   - Enable dynamic promotion threshold

3. Gradient explosion (loss → inf)
   - Add gradient clipping (max_norm=1.0)
   - Reduce learning rate

4. Slow training
   - Enable mixed precision
   - Increase batch size
   - Use Rust MCTS acceleration

## Issue 1: Gradient Explosion (FIXED)

### Symptoms

- All subsequent generations had policy_loss in 10^32-10^33 range

### Root Cause
No gradient clipping was implemented. A single bad batch caused catastrophic gradient updates.

### Fix Applied
Added gradient clipping with `torch.nn.utils.clip_grad_norm_()`:

```python
# In trainer.py TrainingConfig:
max_grad_norm: float = 1.0  # Max gradient norm for clipping

# In training loop (both mixed precision and regular):
torch.nn.utils.clip_grad_norm_(self.network.parameters(), self.config.max_grad_norm)
```

---

## Issue 2: No Policy Learning (DIAGNOSIS COMPLETE, NEEDS ARCHITECTURAL FIX)

### Symptoms
- Policy loss stayed flat at ~4.35 for 36 generations
- Win rate remained random at ~25% (1/4 players)
- Value loss DID decrease from ~1.0 to ~0.08 (value head IS learning)

### Key Insight: Policy Loss = log(num_legal_moves)

```
exp(4.35) ≈ 78
```

A policy loss of 4.35 means the network is predicting near-uniform probabilities over ~78 legal moves. This is the cross-entropy loss when both target and prediction are uniform distributions over N items: `-sum(1/N * log(1/N)) = log(N)`.

### Root Cause: Cold Start Problem

1. **Initial state**: Network outputs uniform policy over all legal moves
2. **MCTS with uniform prior**: Explores all moves somewhat equally
3. **With 800 simulations over 78+ moves**: Visits remain fairly uniform
4. **Training targets**: Near-uniform MCTS visit distributions
5. **Result**: Training on uniform targets reinforces uniform predictions

This is a **chicken-and-egg problem**:
- MCTS needs good policy priors to focus search
- Network needs focused MCTS targets to learn good policies
- Without external signal, the system stays in random equilibrium

### Why Value Head Learns But Policy Doesn't

The value head receives a clear signal: +1 for winner, -1 for losers. Even with random play, the network can learn that:
- Certain board configurations correlate with winning
- Game phase (early/mid/late) affects outcomes
- Piece placement patterns matter

The policy head, however, receives targets that are the output of MCTS **using its own predictions**. When predictions are uniform, MCTS generates uniform targets, creating no learning gradient.

---

## Recommendations to Fix Cold Start Problem

### Option 1: Bootstrap with Handcrafted Heuristics

Add heuristic-based policy biases before MCTS:
```python
def compute_move_prior(move, game_state):
    """Simple heuristics to bootstrap policy learning."""
    score = 1.0

    # Prefer larger pieces early game
    if game_state.turn_number < 20:
        score += PIECE_CATALOG[move.piece_idx].size * 0.1

    # Prefer center positions
    center_dist = abs(move.row - 9.5) + abs(move.col - 9.5)
    score += (1.0 - center_dist / 20.0) * 0.2

    # Prefer moves that create more corner options
    # ... etc

    return score
```

Blend these priors with the neural network output initially, then gradually reduce the blend factor.

### Option 2: Curriculum Learning

Start training on simpler scenarios:
1. **Phase 1**: 1v1 Blokus (2 players, lower branching factor)
2. **Phase 2**: 2v2 team Blokus
3. **Phase 3**: Full 4-player Blokus

This gives the network easier learning problems before tackling the full game.

### Option 3: Increase MCTS Simulations at Root

With more simulations, MCTS can explore more deeply even with uniform priors:
```python
# Current: 800 simulations
# Increase to: 1600-3200 for early training

# After policy starts improving, can reduce back to 800
mcts_simulations: int = 1600  # Double for first N generations
```

### Option 4: Temperature Schedule for Policy Targets

Instead of using raw MCTS visit counts, use temperature-adjusted targets:
```python
# Higher temperature (>1.0) = more exploration = sharper targets
# Lower temperature (<1.0) = more exploitation = softer targets

# Use high temperature initially to create more peaked targets
target_temperature = 0.5  # Makes winning moves more prominent in target
```

### Option 5: Add Policy Entropy Regularization

Add a term to the loss that penalizes uniform predictions:
```python
# Encourage the network to be more confident
policy_entropy = -torch.sum(F.softmax(policy_logits, dim=1) * F.log_softmax(policy_logits, dim=1), dim=1)
entropy_bonus = -0.01 * policy_entropy.mean()  # Negative = penalize high entropy
loss = policy_loss + value_loss + entropy_bonus
```

- model_path: VARCHAR(255) - filesystem path to .pt file
- created_at: TIMESTAMP

Indexes:
- PRIMARY KEY (id)
- INDEX on (run_id)
- INDEX on (run_id, generation)
- INDEX on (is_best)

Foreign Key: run_id → alphazero_runs(id) ON DELETE CASCADE

--------------------------------------------------------------------------------
TABLE: alphazero_metrics
--------------------------------------------------------------------------------
Fine-grained training metrics logged every 50 steps.

Columns:
- id: UUID (primary key)
- run_id: UUID (foreign key → alphazero_runs)
- generation: INTEGER - training generation
- step: INTEGER - step within generation (1, 50, 100, ...)
- policy_loss: REAL - cross-entropy loss on policy
- value_loss: REAL - MSE loss on value
- total_loss: REAL - combined loss
- learning_rate: REAL - current LR (with scheduler)
- grad_norm: REAL - gradient norm before clipping
- step_time_ms: REAL - time per training step
- replay_buffer_size: INTEGER - examples in buffer

Game Heuristics (logged at step=1 per generation):
- avg_corners: REAL - average valid corners per turn
- avg_mobility: REAL - average legal moves per turn
- center_coverage: REAL - ratio of center cells occupied

Policy Quality Metrics (for diagnosing cold start):
- policy_entropy: REAL - entropy of MCTS policy targets
- policy_top1: REAL - probability mass on best move
- policy_top5: REAL - probability mass on top 5 moves

Indexes:
- PRIMARY KEY (id)
- INDEX on (run_id)
- INDEX on (run_id, generation, step)

Foreign Key: run_id → alphazero_runs(id) ON DELETE CASCADE

SAMPLE DATA: Training Run Comparison
--------------------------------------------------------------------------------

This data shows the dramatic difference between training WITH and WITHOUT
heuristic pretraining:

Run: "SM" (NO pretraining)
| Gen | Policy Loss | Entropy | Top-1  | Top-5  | Win Rate |
|-----|-------------|---------|--------|--------|----------|
|  1  |    4.4412   |  4.437  | 0.0699 | 0.1880 |   40%    |
|  2  |    4.4844   |  4.391  | 0.0743 | 0.2082 |   20%    |

Run: "SM WITH PRETRAINING" (WITH heuristic pretraining)
| Gen | Policy Loss | Entropy | Top-1  | Top-5  | Win Rate |
|-----|-------------|---------|--------|--------|----------|
|  1  |    2.5641   |  2.291  | 0.4046 | 0.6719 |  100%    |
|  2  |    2.0860   |  1.542  | 0.5515 | 0.8471 |   50%    |

Key observations:
1. WITHOUT pretraining: Policy loss ~4.4 = log(~80 moves) = uniform distribution
2. WITH pretraining: Policy loss ~2.0 = log(~7 moves) = focused distribution
3. Entropy drops from 4.4 to 1.5 with pretraining
4. Top-1 probability jumps from 7% to 55% with pretraining
5. First generation win rate: 40% vs 100% (pretraining helps immediately)

-- Training progress over generations
SELECT generation, 
       AVG(policy_loss) as avg_policy_loss,
       AVG(value_loss) as avg_value_loss,
       AVG(policy_entropy) as avg_entropy
FROM alphazero_metrics 
WHERE run_id = 'YOUR_RUN_ID'
GROUP BY generation
ORDER BY generation;

-- Find generations where policy started learning
SELECT generation, policy_entropy, policy_top1
FROM alphazero_metrics
WHERE run_id = 'YOUR_RUN_ID' 
  AND step = 1
  AND policy_entropy < 3.0  -- Below uniform
ORDER BY generation;

-- Check for gradient explosion
SELECT generation, step, policy_loss, value_loss
FROM alphazero_metrics
WHERE run_id = 'YOUR_RUN_ID'
  AND (policy_loss > 100 OR value_loss > 100 OR policy_loss IS NULL)
ORDER BY generation, step;

-- Best models by win rate
SELECT c.generation, c.eval_win_rate, c.is_best, r.name
FROM alphazero_checkpoints c
JOIN alphazero_runs r ON c.run_id = r.id
WHERE c.eval_win_rate > 0.5
ORDER BY c.eval_win_rate DESC;
